# 翻譯模型比較：gemini-4-hydrogen / gemini-4-neon / gemini-3.1-pro，與 refine 的 gpt-6.1-sol / gpt-6.2-sol

日期：2026-11-21

## 結論

- **hydrogen 對 3.1 Pro**：hydrogen 的初稿口語比較自然、briefing 人物表比較完整、chunk 也比較快。缺點是遇到 ASR 爛掉的句子時，會寫出通順但意思錯的話。3.1 Pro 偏直譯，錯的時候比較容易一眼看出來。
- **neon 對 hydrogen**：在同一集、同樣條件的 A/B 測試中，neon 明顯比較能聽懂「誰對誰說了什麼」。8 個已知錯誤中，neon 翻對 7 個、部分對 1 個；hydrogen 重跑只翻對 2 個。代價是速度：chunk 慢約 1.7～1.9 倍，prepass 慢約 1.5 倍。這只是一集、兩個 chunk 的結果。
- **refine 用 gpt-6.2-sol 對 gpt-6.1-sol**：在同樣是 ultra effort、prompt 沒改的情況下，6.2 實質修改的字幕約是 6.1 的 3～4 倍。抽樣看到的多半是改善，例如刪掉多餘注解、精簡句子、修正主詞。事後的 proofread 修改率沒有上升。
- **測量注意事項**：refine 修改率很受 refine 模型影響，只能在同一個 refine 模型下拿來比較 chunk 模型。同一個模型同一段重跑，用字差異就有 37～47%，所以不能用用字差異判斷模型好壞，要用固定的已知錯誤清單來比。

### 譯文讀起來的差別（大悟的芸人領収書，同段約 45 則）

- **3.1 Pro 偏直譯**：例如「這個姑且是長這樣的」「說實話是的」「所以你要思考如何為了不發暖暖包而想出段子」，多半靠 refine 修順。ASR 爛掉的地方會照字面硬翻，例如「只有Yes嗎 因為很溫暖嘛」。
- **hydrogen 口語自然**：例如「就是說啊」「不然把經紀人也找來，三個人去喝一杯怎麼樣」。但遇到含糊的句子會寫出通順的錯話，例如把「涮涮鍋又不是西本專屬的」翻成反義、把「能在只有我們兩個時再說一次嗎」翻成「我真的會只找你兩個人去一次啦」。因為讀起來很順，這類錯比直譯錯更難發現。

## 2. refine：gpt-6.1-sol 對 gpt-6.2-sol

### 條件

- 兩者都是 `codex/<model>/ultra`。
- refine prompt 在切換前後沒有修改。
- 切換前後的 chunk 都有 3.1 Pro 和 hydrogen。

### 修改率

下表的「實質修改」已扣掉只動空白與標點的修改，這類修改的影響可以忽略。

| chunk 模型 | refine 6.1 | refine 6.2 |
|---|---|---|
| 3.1 Pro | 0.15（45 集，範圍 0.09～0.44） | 0.45（2 集） |
| hydrogen | 0.08（4 集） | 0.31（8 集，範圍 0.25～0.42） |
| neon | – | 0.31（1 集） |

不論 chunk 模型是哪一個，6.2 修改的字幕都約是 6.1 的 3～4 倍；用字數算的修改量也約多 3 倍。

### 其他觀察

- **耗時**：refine 中位數約 500 秒變成約 600 秒；glossary check（同樣換成 6.2）約 420 秒變成約 590 秒。
- **token**：輸出 token 略多（約 16k 變 20k），reasoning token 反而較少。
- **glossary check 修改率**：約 1.5% 升到 2～4.5%。
- **proofread（claude-opus-5-5）修改率**：前後都在 0.2～0.6%，沒有因為 6.2 改得多而跟著增加。

### 6.2 多改了什麼（抽樣讀兩集各 40～50 則）

- **刪掉多餘的括號注解**：例如「擊面（面）」「一本（有效擊中）」「身體衝撞（體當）」。
- **精簡冗長句**：例如「各位可以看到，兩人的體格幾乎旗鼓相當」改成「看得出兩人的體格不相上下」。
- **接順跨則的句子**：例如「實力上會展現出、／什麼樣的實力差距呢？」改成「至於兩人的實力……／又會有多大的差距呢？」。
- **修正主詞與內容**：例如把「雙方都展現出」改成「大須賀展現了」，刪掉 chunk 自行加上的人名。
- **少數純口味調整**：例如「國民」改成「全民」。

這次抽樣沒有看到明顯改錯的地方。

### 設計

- **測試集數**：2026-11-16 的《大悟の芸人領収書》，396 則字幕、4 個 chunk。原本由 hydrogen 翻譯。
- **答案卷**：當時 refine（6.1）的報告列出 hydrogen 在這集的 10 處錯誤，其中 8 處落在 `0098-0195` 和 `0296-0396` 這兩個 chunk。

- **變動基準**：每個 chunk 都讓 hydrogen 再跑一次，用來看同一個模型重跑本身會差多少。

### 答案卷以外的觀察

- **neon 做得比較好**：

- **neon 做得比較差**：
  - #344–345 是無意義的發音梗，neon 音譯成中文字「蘇、塞、索」「奇吉」；hydrogen 存檔保留拼音（Su、Se、So／Kiji），refine 報告也主張保留發音。

- **neon 多抓到的人物**：助理主持黑田みゆ，以及只在對話中被提到的宮本亞門、寺門ジモン、小峠英二、尾形貴弘。前團員則補上全名「海野裕二」。
- **關鍵段落的人物關係**：hydrogen 在 98–195 的段落摘要寫「拍 OL 影片時 Kamichii 睡著」，實際上睡著的是西本。refine 報告也指出 briefing 在這裡把人物關係放錯，這可能就是 hydrogen 存檔版 #116、#123 翻錯的原因。neon 寫對了，也看出 Kamichii 最愛吃的其實是刨冰。
- **其他 neon 段落摘要抓對的地方**：#261「這家電視台竟然敢用林田」、#298「超力量系」的對比。hydrogen 在 #298 寫錯了。

## 4. 方法

### 歸檔統計（第 1、2 節）

- 每集從 `.work/*/session/result.json` 讀取 backend、model、effort、耗時與 token 用量。
- 字幕逐則比對 `09_chunks/merged.srt`（chunk 輸出）和 `10_refine/refined.srt`（refine 輸出）。
- 「實質修改」是指去掉空白與標點後內容仍然不同的修改。
- 以同節目、相鄰週次配對。

### 低額度 A/B（第 3 節）

1. 把專案複製到一個獨立的 `GRILL_HOME`。`grill.toml` 只改 `[agents.roles]` 的 `prepass`、`chunk`，以及 `[paths]`，讓 archive 和 package 都指向這個獨立目錄。只需要帶 `project.json`、`video.mp4`、`.subs/ja.srt`、`.subs/ja.voiced.srt`，以及 `.work` 底下的 `01_metadata`、`05_audio`、`08_prepass`、`09_chunks`。
2. 從 `project.json` 的 `stages` 移除要重跑的 stage 以及之後的所有 stage。
3. **重跑 chunk**：只刪掉目標 chunk 的 `translation.json` 和 `session/`。其他 chunk 因為檔案還在，會被當成 cache 直接沿用（chunk cache 只看檔案是否存在）。接著執行 `grill <id> --break-after chunks`。
4. **重跑 prepass**：刪掉 `08_prepass/briefing.json` 和 `session/`（保留 `frames/`），執行 `grill <id> --break-after prepass`。
5. 每次執行完都把目標的 `translation.json` 或 `briefing.json` 另存一份，再準備下一組。

**成本**：每個 chunk 1 次 agent 呼叫，prepass 也是 1 次；不會用到計費的 ASR 或 watch_clip。

### 限制

- A/B 只有一集、兩個 chunk、每個模型各一次。
- 答案卷來自 refine 6.1 加上 proofread 的最終成品，不一定完全正確。
- 3.1 Pro 搭配 refine 6.2 只有 2 集，而且都是 YouTube 短片。
